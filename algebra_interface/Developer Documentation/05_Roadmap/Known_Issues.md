### Lessons from D8, D9 and D10

All the project's lessons, these included, are gathered in [Lessons](../03_Developer_Guides/Lessons.md). Add new defect lessons here with their evidence, and a short entry there.

1. **Every part a student can point at needs a box of its own.** The `+` in `2(x + -y)` belongs to a sum that has no box, so anything aimed at the `+` lands on the nearest box: the whole bracket. This is renderer decision R1, already approved: every `Add` and `Multiply` gets its own box. D8 is evidence that R1 matters for what students see, not just for code tidiness.
2. **One owner for "what is highlighted now".** Hover is painted by two independent systems: CSS `:hover`, which matches the hovered element *and every ancestor*, and the JavaScript `is-hitbox-hovered` class, which picks one box. The rule `.term:has(.term:hover):hover` only stops the ancestor glow when a child *box* is hovered, not when an operator or a gap is. Standard 4 (decoration after rendering, by identity) and stage 5 should make the decoration layer the only painter, and retire `:hover` as a source of meaning.
3. **Feedback must follow the view mode.** During a drag, only drop-target feedback should show; ordinary hover belongs to `idle`. The view mode (stage 2) now knows when a drag is in progress, so the decoration layer can ask it, the same way the router does.
4. **Silence is also feedback.** Since D7, hovering over the term's own place shows no target, which is correct for commits. But with nothing else on screen, a stray hover glow became the only signal. A neutral "this is where it came from" mark would tell the student the truth.
6. **D8 was really two defects, and I explained only one.** The owner's first picture showed both the bracket glow (D8) and the grown copies (D9). My first hypothesis was the D9 cause; a probe with off-screen coordinates found no preview copy, and I dropped that hypothesis instead of fixing the probe. The second report showed the picture was unchanged. Lesson: when a probe contradicts a hypothesis, check the probe first, and check that the fix makes the *reported picture* disappear, not just the part that was understood.
7. **Copies of the mathematics must carry the same scope.** Anything rendered outside `#equation` that shows mathematics needs `.math-scope`, or scoped CSS silently stops applying. A stylesheet test now guards the rule side; new copies must add the class.
8. **One structural fix can remove several defects.** R1 (a box for every nested sum) fixed D8's glow and D10's wrong target, because both came from the same gap: a part the student could point at that belonged to no box.
5. **Reproduce it before explaining it.** The first attempts used off-screen coordinates, so the drag never started; they looked plausible but tested nothing. Checking the view mode (`manipulatorDiagnostics.mode()`) showed the drag hadn't begun. Probes should assert that they reached the state they claim to test.
9. **A rename must cover shorthand, and errors must not vanish** (stage 6a, 12 November 2026). Splitting `state` renamed every `state.x`, but missed the shorthand `{ state, staged }` passed to `publishPreparedTransformation`. That threw a ReferenceError on every commit, and something on the drop path swallowed it: the page showed no error, the drop simply did nothing. The Node tests passed; the browser tests caught it. Prevention: `tests/app/state-split.test.js` forbids a bare `state` in `app.js`, and every step now runs the browser suite before its commit. It happened again in stage 6e (an `as` alias import was not carried into `ordinaryDragView.js`; the browser suite caught it before commit), so `tests/architecture/free-names.test.js` now checks, without running the code, that every name used by `app.js` and the modules moved out of it is declared, imported or a known global. **Update (12 November 2026):** the error was not swallowed, it reached only the console as an uncaught page error, so the student saw nothing. A rule's drop that throws is now caught by the shared drag view, which clears the drag and shows "That step could not be completed; the expression is unchanged." (checked by putting a broken commit back temporarily). Other paths (previews, toolbar commands) still report only to the console.
10. **A general rule must be checked against every case it replaces** (stage 6f, 12 November 2026). Replacing "no hover outline during the grouping, factorisation and distribution previews" with "hover outline only when idle" also removed it from equality's confirm targets, which the student clicks. The screenshots caught it (`equality-preview-hovered`). The first fix (outline on every confirm target) then broke factorisation's, which draws its own hover style. The rule that matches every case: during a preview, only confirm targets marked `data-preview-confirm` get the general outline, and a target with its own hover style is not marked. Prevention: the screenshot suite covers hovered preview states; run it before every commit, and read each difference before deciding it is expected.
11. **Building a rule is the real test of a design** (stage 7, 12 November 2026). Every earlier check said the rules were separate, yet the first rule built from scratch found two places that still listed the rules: three lists of bundles, and hard-coded drop-target kinds in the shared arbiters (a new kind's drop was refused silently, with no error). Both are now generic and tested. Prevention: when shared code needs to know "which rules exist", it asks the registered extensions, never a list of names; `tests/view/drag/rule-drop-arbitration.test.js` and `tests/architecture/rule-bundle-list.test.js` hold this.
12. **Two shapes with similar names invite mistakes** (cancel-opposites, 12 November 2026). A feature's `propose(root, …)` returns the Engine's result, but `ctx.propose(request)` returns a candidate `{ action, result }`. The new bundle committed `candidate.root` (undefined); the Engine tests passed because they called the feature directly. Prevention: the shape is written in the rule-context list (`js/rules/negation/install.js`) and in the guide, every rule has a browser test of its real install path, and a failing drop is now visible.

13. **A clash that only a browser shows needs a check that runs everywhere** (stage E4b, 12 November 2026). The new identity-rules bundle named a route `identity-preview-outside`, a name the identity-element bundle (+0, ×1) already used. The input router refuses a repeated name when the page starts, so the whole page stopped working. All Node tests still passed, because a bundle is installed only in a browser. **Prevention:** `tests/architecture/rule-bundle-boundaries.test.js` now reads every `route({ name: … })` in the rules, views and interaction code and fails on a repeated name. Changing the name back makes it fail. A second lesson from the same step: a browser suite started before an edit and still running during it tests a mixture, so suites now run only on a finished change.

14. **Data read at start-up must not use up document state** (stage E4b, 12 November 2026). The identity rules read their patterns when the page loads, and each pattern node took a document node ID, so every document's IDs moved up. The screenshot suite saw it: the structure label, which shows an ID, grew wider in 166 screenshots. Nothing was wrong mathematically, but a definition should not change what a student's document receives. **Fix and prevention:** pattern nodes take their own `pattern-n` IDs (`buildPattern` in `js/engine/nodeFactory.js`), and a Node test checks that reading the patterns leaves the document ID counter unchanged.

## Accepted technical limitations and architectural risks

**Drag target during a visible preview (from the D7 fix):** while a rearrangement preview is on screen, a position means whatever the preview shows there, so the original `+` position can mean a rearrangement. A pointer path that crosses a gap can also start a new preview that moves the target. This follows the rule that a rearrangement is seen before it commits. Review if classroom use shows students struggling.

## Historical dispositions

- **Equation-side gestures (stage 7 follow-up, resolved 12 November 2026).** (1) A single-term side such as the `x` of `x = 2y+3` could not start a drag, so the both-sides rule was unreachable from it. The drag controller now accepts a whole side (a named slot, `left` or `right`), and the source check verifies that slot as strictly as a numbered one. (2) The both-sides declaration matched terms inside brackets too. Parts now carry `sideTerm` (a whole side, or a term of a sum that is a side, read from the side's R1 box), and the rule declares on it. While testing, dropping a side on no target said "The drag is no longer valid"; the drop decision now passes "none" through as a plain cancel ("Move cancelled").

**D1 and D2, fixed in interaction step 2:** signed factors now show a multiplication sign (`b · −c`) through one notation rule shared by renderer and text printer, and the parser reads them. See `tests/engine/signed-factor-notation.test.js`.

**D3 and D4, fixed by exact numbers (10 November 2026):** 12-digit rounding gave wrong values (`1000000000000 + 1` gave `1000000000000`, and a typed `1234567890123` displayed as `1234567890120`), and equality compared assigned decimals inexactly (`0.1 + 0.2 = 0.3` was false). Numbers are now exact rationals in `js/engine/rational.js`; covered by `tests/engine/rational.test.js` and `tests/engine/exact-numbers.test.js`.

**D7, fixed in T4-4:** a quick release on a valid target was silently cancelled during a preview return animation. This explained the earlier "second distribution drag" reports. See the [T4-4 record](../04_Testing/T3_to_T5_Test_Quality_Execution_Plan.md).

Phase 0 highlighted shared visual-feedback ownership, duplicated semantic targeting and scattered interaction/preview responsibilities. Phases 1–4 introduced dedicated feedback ownership, semantic target resolution, arbitration and modal-preview leases, with retrospective verification. **The original concerns motivated completed work; their exact historical wording is not an open issue list.** Likewise, the old “negation v1.2.3 browser verification pending” note is superseded by later accepted releases.
