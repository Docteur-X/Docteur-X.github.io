## Accepted technical limitations and architectural risks

| Area | Current boundary | Trigger for action |
| --- | --- | --- |
| FLIP animation callback lifetime | Delayed callbacks are not generation-invalidated. Full rerender usually detaches old nodes; no current interference defect demonstrated. | DOM reuse, multi-view changes, or browser reproduction of callback interference. |
| Exceptional presentation recovery | Lease release is attempted across modal families, but a failed DOM/renderer cleanup does not guarantee full visual restoration. | Controlled fault-injection or a reproducible stranded-view defect; design cross-family recovery policy. |
| Modal preview integration coverage | Registry contract covers all 30 directed family conflicts; real-browser cross-family conflict coverage is representative, not exhaustive. | Add targeted interactions when changing preview entry paths or shared ownership. |
| Multi-view assumptions | View-local components have isolation contract tests, but the application still composes one active mathematical view. | Phase 6 design approval and source-level multi-view characterization. |
| Dependency checker | Static import guardrails are deliberately narrower than a full JavaScript parser. | New syntax, dynamic-import policy changes, or new directory/layer ownership. |
| Mathematical domains and assumptions | General domain/type/assumption reasoning and broad calculus/algebra operations are not yet implemented. | A specific mathematically scoped feature proposal with validity and teaching-policy requirements. |
| Performance | No low-end-device performance guarantees; large expressions and histories may need measurement. | Profile actual bottlenecks before optimization. |

## Historical dispositions

Phase 0 highlighted shared visual-feedback ownership, duplicated semantic targeting and scattered interaction/preview responsibilities. Phases 1–4 introduced dedicated feedback ownership, semantic target resolution, arbitration and modal-preview leases, with retrospective verification. **The original concerns motivated completed work; their exact historical wording is not an open issue list.** Likewise, the old “negation v1.2.3 browser verification pending” note is superseded by later accepted releases.

## Maintenance rules

Classify each new report as **confirmed defect**, **observed/unreproduced behaviour**, **accepted limitation**, or **deferred enhancement**. Do not silently upgrade speculation to fact, or mark an issue resolved without evidence. Update this file when relevant source, tests or decisions change; preserve older chronology in historical records rather than appending stale “current” headings.
